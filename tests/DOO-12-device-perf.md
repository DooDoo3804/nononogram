# DOO-12 — 실기 안드로이드 60fps 실측

**판정: 미해결. 블로커 유지.** 이 환경에서는 "중간 크기 안드로이드 60fps"를 판정할 수
없다. 추측으로 통과시키지 않는다.

측정 기준 커밋 `786713e`, 측정일 2026-10-06. 측정 중 다른 트랙(DOO-19)이 `bench/bench.js`에
DPR 캡 노브를 추가했으므로, 3절 수치는 **그 변경 이전** 산출물에 대한 것이다.

**2026-10-06 갱신 (`af5ea54`·`8034d51` 이후).** Vitra가 모바일 드로잉 버퍼를 1배 →
min(DPR, 2)로 올렸다. 폰이 그리는 픽셀이 2.7배로 늘었고, 캡 2의 근거는 M1 Pro 실측을
문헌값 5~10배로 나눈 **투사**이며 `render/scene.js`가 그 근거 옆에 "실기 수치는 DOO-12에
남아 있다"고 적어 두었다. 즉 DOO-12는 이제 60fps 체크 하나가 아니라 **출고된 DPR 캡의
근거**까지 받치고 있다. 그래서 5절을 추가했다 — 폰 왕복 1회로 두 질문을 다 닫는다.

## 1. 실기·에뮬레이터 부재 재확인

이슈 본문의 주장을 독립적으로 다시 확인했다. SDK 자체는 깔려 있으나 PATH에 없을 뿐이고,
**실행할 수 있는 안드로이드가 없다**는 결론은 같다.

```
~/Library/Android/sdk/platform-tools/adb devices   -> List of devices attached (비어 있음)
~/Library/Android/sdk/emulator/emulator -list-avds  -> (비어 있음)
~/.android/avd                                      -> 없음
~/Library/Android/sdk/system-images                 -> 없음
```

AVD를 만들 시스템 이미지조차 없다. 그리고 QA는 배포 권한이 없으므로 공개 URL을 만들어
해결할 수도 없다. **사람이 폰으로 열어야 한다**는 이슈의 전제는 유효하다.

## 2. 사람이 해야 할 일을 2분으로 줄였다 — `tests/phone-bench.mjs`

이슈는 "배포 → 폰에서 URL 열기 → 패널 캡처 → 수치 전사"를 요구했다. 배포도 전사도 없이
같은 결과를 얻도록 하네스를 만들었다.

```
npm run build
node tests/phone-bench.mjs
```

노트북이 LAN 주소를 출력한다. 같은 Wi-Fi의 안드로이드 폰 브라우저에서 그 주소를 열고
화면을 켠 채 약 90초 두면 끝이다 (5절의 DPR 스윕이 추가되어 70초에서 늘었다). 폰에는
아무 설치도, 빌드도, 개발자 설정도 필요 없다.

하네스가 대신 해주는 것:

- **기기 신원 자동 기록** — UA-CH `getHighEntropyValues`로 기종명, OS 버전, 화면 해상도,
  DPR, 코어 수, 메모리, 네트워크, GL 렌더러 문자열을 수치 옆에 붙인다. "중간 크기
  안드로이드"는 하드웨어에 대한 주장이므로 사람의 기억이 아니라 기록이 필요하다.
- **전사 제거** — 결과가 노트북으로 POST되어 `verify-out/phone-bench-<기종>-<시각>.json`에
  저장된다. 13열 표를 스크린샷에서 손으로 옮기다 틀릴 일이 없다.
- **화면 주사율 실측** — 90/120Hz 폰의 프레임 예산은 16.7ms가 아니라 11.1/8.3ms다. p95를
  어느 예산에 대고 읽어야 하는지 알려면 주사율을 알아야 한다.
- **발열 스로틀링** — 노트북이 재현할 수 없는 바로 그 축이고, 4초 윈도 한 번으로는 안
  드러난다. 스위트를 연속 2패스 돌려 패스2 p95를 패스1과 크기별로 비교한다 (1.25배 초과 시 실패).
- **오염된 측정 차단** — 화면이 꺼지거나 탭이 가려지면 rAF가 멈춰 "0 dropped, 60fps"라는
  거짓 통과가 나온다. 측정 중 `document.hidden`이 한 번이라도 참이면 tainted로 표시하고
  재측정을 요구한다.
- **판정을 폰 화면에 렌더** — 항목별 ok/FAIL 카드가 떠서 스크린샷 하나로 근거가 된다.
  판정 규칙은 서버에만 있고 응답으로 돌려주므로, 저장된 기록과 폰 화면이 어긋날 수 없다.

`bench/`는 손대지 않았다. 동일 출처 iframe을 전체 화면 크기로 띄워 기기의 실제 해상도로
렌더하게 하고, `scripts/bench-render.mjs`가 이미 쓰는 `window.__bench` 계약만 읽는다.
아무것도 배포하지 않고 LAN을 벗어나지 않는다.

**하네스 자체를 검증했다.** 에뮬레이트된 폰(412x915@2.625, Pixel급)으로 끝까지 돌려
JSON 저장·판정 카드 렌더까지 확인했고, 그 과정에서 아래 BUG-C를 잡아 고쳤다. 사람이
한 번에 성공하도록 미리 돌려본 결과다.

## 3. 이 환경에서 확보한 하한선 — `tests/gpu-bench.mjs`

3회 반복, 프로파일별 1분 부하 평균 기록. 전체 원자료는 `verify-out/bench-gpu.json`
(`verify-out/`는 gitignore 대상이라 로컬에만 있다. 재생성: `BENCH_REPS=3 node tests/gpu-bench.mjs`).

| 프로파일 | 3³ p95 | 4³ p95 | 5³ p95 | 6³ p95 | first frame | 드로우콜 |
|---|---|---|---|---|---|---|
| hw-metal / cpu 4배 | 17.5–18.0 | 17.2–17.9 | 17.6–17.9 | **17.6–17.8** | 176–199ms | 9 (상수) |
| hw-metal / cpu 6배 | 17.8–18.1 | 17.9–18.0 | 17.7–18.0 | **17.8–18.0** | 236–321ms | 9 (상수) |
| swiftshader / cpu 4배 | 17.7–17.8 | 17.6–18.1 | 17.6–**27.2** | **20.9–25.7** | **2050–3180ms** | 9 (상수) |

뷰포트는 전부 412x915 @ DPR 2.625 (1082x2402px). cpu/프레임은 모든 칸에서 0.24–0.79ms로
예산(16.7ms)의 5% 미만이었다.

하드웨어 독립적이라 폰에 그대로 전이되는 것: **드로우콜 9개가 3³부터 6³까지 12회 측정
전부에서 상수**, 레이캐스트 피킹 전 크기 성공, 삼각형 수 1710(6³). 이건 통과다.

전이되지 않는 것: fps·p95·cpu·first frame. 아래 BUG-A 때문에 기존 수치는 GPU 축에서
비관적이지 않았고, 실제 폰의 GPU 대역폭·발열·브라우저 합성기는 여전히 미측정이다.

## 4. 버그

**상태 (2026-10-06 갱신).** BUG-A와 BUG-C는 Vitra가 `8034d51`에서 고쳤다 — 게이트가
플래그로 백엔드를 추론하지 않고 `page.glRenderer()`로 페이지에서 실제 값을 읽어 기록하고,
드로우콜 체크는 "증가하지 않음 + 상한 12"로 완화됐다 (내 하네스와 같은 기준). BUG-D도
`os.loadavg()` 기록 + 부하 초과 시 advisory 강등으로 반영됐다. BUG-B는 소프트웨어 래스터
한정이고 폰 판정이 아니므로 그대로 둔다. 아래는 원 리포트를 기록으로 보존한 것이다.

### BUG-A — 성능 게이트가 실제와 다른 GL 백엔드를 문서화하고 있다 (영향: 중) — **고쳐짐 `8034d51`**

- **재현** `node tests/gpu-bench.mjs` 또는 `scripts/bench-render.mjs`의 플래그
  (`--use-gl=angle --enable-unsafe-swiftshader`)로 Chrome을 띄우고 `WEBGL_debug_renderer_info`의
  `UNMASKED_RENDERER_WEBGL`을 읽는다.
- **기대** 주석대로 SwiftShader 소프트웨어 래스터라이저.
- **실제** `ANGLE (Apple, ANGLE Metal Renderer: Apple M1 Pro, Unspecified Version)` — 실제
  하드웨어 GPU. 3/3 반복 동일. 저 플래그는 소프트웨어 폴백을 *허용*할 뿐 강제하지 않는다.
  강제하려면 `--use-angle=swiftshader`가 필요하다.
- **파급** `bench-render.mjs`의 "both knobs err pessimistic, so a pass here is a floor"라는
  추론이 CPU 축에만 해당한다. GPU 축에서는 M1 Pro가 어떤 중급 안드로이드 GPU보다 빠르므로
  기존 수치는 **낙관적**이다. 이슈 본문의 "헤드리스 데스크톱/감속" 표도 같은 라벨을 물려받았다.
  DOO-12를 추측으로 닫을 수 없는 이유가 하나 더 늘었다. 소유 트랙(플랫폼)에 주석 수정 요청.

### BUG-B — 소프트웨어 래스터 6³에서 p95 예산 초과, 3/3 재현 (영향: 조사 필요, 폰 판정 아님)

- **재현** `BENCH_REPS=3 node tests/gpu-bench.mjs` → `swiftshader/cpu4` 프로파일.
- **기대** p95 ≤ 20ms.
- **실제** 6³에서 20.9 / 23.1 / 25.7ms (3회 전부 초과), dropped 5–14프레임. 5³도 1회 27.2ms.
  같은 칸의 cpu/프레임은 0.24–0.35ms.
- **해석** cpu 0.3ms 옆의 23ms 프레임은 CPU 하류의 비용이다. 즉 프레임 코스트가 fill 축에
  민감하고, "드로우콜이 상수"는 이 축을 덮지 않는다. 중급 안드로이드가 가장 약한 축이
  바로 여기다. **단, 이것은 폰에 대한 판정이 아니다** — 어떤 폰 GPU도 소프트웨어 래스터만큼
  fill이 나쁘지 않고, 이 측정은 데스크톱 메모리 서브시스템 위에서 발열 스로틀링 없이 돌았다.
  DOO-19가 `?maxdpr` 노브로 이 축(버퍼 면적 대비 fill 코스트)을 이미 다루고 있어 중복
  측정을 하지 않았다. 폰 측정에서 6³ p95가 흔들린다면 1순위로 볼 곳이다.

### BUG-C — 드로우콜 상수 체크가 종횡비에 의존해 오탐한다 (영향: 하, 게이트 신뢰성) — **고쳐짐 `8034d51`**

- **재현** 412x915 iframe 안에서 `bench/`를 돌린다 (`tests/phone-bench.mjs`의 경로).
- **기대** 드로우콜 9개 상수.
- **실제** 3³/4³에서 9, 5³/6³에서 **8** (삼각형도 930→928, 1710→1708). 기즈모의 축 라벨
  스프라이트 하나가 카메라 프레이밍에서 절두체 컬링된 것으로, 셀 수와 무관하다.
- **파급** `scripts/bench-render.mjs`는 `calls.size === 1` 엄격 일치를 단정한다. 1280x860과
  전체 화면 412x915에서는 통과하지만 다른 종횡비에서는 **셀 수와 무관한 이유로 실패**한다.
  폰 종횡비는 기기마다 다르므로 실기 측정이 스퓨리어스 실패할 수 있었다. 내 하네스 두 개는
  "셀 수에 따라 증가하지 않음 + 상한 12" 기준으로 고쳤다 (예산의 취지가 '증가하지 않음'이다).
  소유 트랙에 게이트 완화 요청.

### BUG-D — 성능 측정이 머신 부하를 기록하지 않아 재현되지 않는다 (영향: 중, 측정 신뢰성) — **고쳐짐 `8034d51`**

- **재현** 이 머신에서 동일 설정을 반복 측정한다. 이 워크스페이스는 다른 에이전트 런과
  공유되고 있다 (측정 중 1분 부하 평균 6.6–15.3, 코어 8개).
- **기대** 같은 설정 → 같은 수치.
- **실제** 같은 설정에서 first frame 144ms ↔ 3006ms, 소프트웨어 래스터 6³ p95 17.6ms ↔ 98.5ms.
  **약 10배 변동.** 첫 측정에서 본 98.5ms/12.3fps 붕괴는 재현되지 않았고 경합으로 판단한다
  (재현되는 값은 BUG-B의 20.9–25.7ms다).
- **파급** 기존 DOO-7/DOO-12 수치에는 부하 기록이 없어, 단일 샘플이 경합을 포함했는지
  판별할 수 없다. 흥미롭게도 하드웨어 GL 경로는 부하 15.3에서도 17.6–18.1ms로 흔들리지
  않았다 — 헤드룸이 그만큼 크다는 증거로, 이건 좋은 신호다. 권고: 게이트가 `os.loadavg()`를
  기록하고 임계 초과 시 판정을 거부할 것. `tests/gpu-bench.mjs`는 그렇게 구현해 두었다.

## 5. 폰 하네스가 채움(fill) 축에 눈이 멀어 있었다 — 고침

### BUG-E — 프레임 열만 보고하는 폰 측정은 DPR 캡에 대해 거짓 통과를 낸다 (영향: 상)

- **재현** `node tests/phone-bench.mjs`를 `8034d51` 이전 버전으로 돌린다. 보고되는 열은
  fps·p95·cpu·dropped·first frame뿐이다.
- **기대** 수치가 "캡 2가 이 폰에서 안전한가"에 답한다.
- **실제** 답하지 못한다. `p95`는 vsync에 묶이고 `cpuMs`는 우리 코드만 괄호 친다. GPU는
  비동기로 래스터하므로 버퍼를 몇 배로 키워도 vsync를 **놓치기 직전까지** 똑같이 60.0fps가
  찍힌다. 이번에 직접 재현했다 — 에뮬레이트된 폰에서 캡을 1 → 2.625배로 쓸면서:

  | 캡 | 버퍼 | 버퍼 픽셀 | **p95** | sync | sync p95 | dropped |
  |---|---|---|---|---|---|---|
  | 1 | 1.000x | 351,848 | **17.60** | 1.70 | 2.10 | 0 |
  | 1.5 | 1.500x | 791,658 | **17.30** | 1.90 | 2.60 | 0 |
  | 2 | 2.000x | 1,407,392 | **17.70** | 2.40 | 3.80 | 0 |
  | 2.625 | 2.625x | 2,422,521 | **17.50** | 3.20 | 3.90 | 0 |

  **p95는 버퍼가 6.9배 커지는 동안 17.3–17.7ms로 완전히 평평하다.** 같은 구간에서 `sync`는
  1.70 → 3.20ms로 단조 증가한다. DOO-19가 이 환경에서 관찰한 것과 같은 현상이고,
  폰에서도 그대로 재현될 성질이다 (vsync 캡은 기기와 무관하다).
- **파급** 사람의 폰 왕복은 1회뿐인데, 고치기 전 하네스는 **어떤 폰에서도 ✅ 통과를 냈을
  것이다** — 그 폰이 캡 2에서 프레임을 놓치기 직전이어도. 캡 2의 근거는 투사로 남고, 두
  번째 왕복을 부탁해야 했다.
- **고침** `tests/phone-bench.mjs`에 채움 축을 넣었다 (`bench/`는 여전히 무수정, 쿼리
  파라미터와 `window.__bench` 계약만 사용):
  - 스위트 행에 `sync`/`syncP95`/`pixelRatio`/`bufferPx` 열 추가.
  - **3단계 DPR 캡 스윕** — 최악 크기(6³)를 캡 1·1.5·2 + **기기 자신의 DPR**로 돌린다.
    기기 DPR을 넣는 이유는 캡이 선명도를 얼마나 깎았는지도 같이 기록하기 위해서다.
    캡이 필요 없었다면 그것도 수치로 보여야 Vitra가 판단할 수 있다.
  - **ms/메가픽셀 회귀** — `sync` 대 버퍼 면적 최소제곱. 기울기가 이 폰의 채움 속도이고,
    절편이 면적과 무관한 비용(드로우콜 제출, readPixels 왕복)을 흡수한다. 캡 결정에
    단일 절대값이 아니라 회귀가 필요한 이유가 이것이다. DPR 1.5 폰처럼 캡 1.5와 2가 같은
    버퍼로 눌리는 경우를 위해 **서로 다른 버퍼 크기 3개 미만이면 회귀를 포기한다**
    (반복된 x에 직선을 끼우면 없는 기울기가 기록에 남는다).
  - 판정 3줄 추가: `sync p95 ≤ 16.7ms`, `버퍼 = min(DPR, 2)`(setPixelRatio 생존 확인),
    `측정된 채움 속도로 캡 2에 헤드룸이 있는가`.
  - **DPR이 2 미만인 폰은 캡을 시험할 수 없다**는 사실을 판정 카드에 명시한다. 약한 시험이
    강한 시험인 척하지 않게 하려는 것이다.

### 부수 확인 — Vitra의 M1 Pro 채움 속도 독립 재현

같은 스윕에서 이 하네스가 뽑은 값: **0.742 ms/메가픽셀** (r² 0.993, 4점, 절편 1.38ms).
`render/scene.js`가 412x915 뷰포트에 대해 적은 값은 0.95 ms/Mpx다. 측정 경로도 다르고
(스위트 iframe 경유) 1분 부하 평균 7.1(코어 8개)에서 잰 값이라 ±25%는 예상 범위이며,
**Vitra의 M1 Pro 기준선은 독립적으로 재현된다**. 캡 2의 남은 불확실성은 기준선이 아니라
"폰 GPU가 M1 Pro의 몇 분의 1인가"라는 **문헌값 5~10배 나누기**에 있고, 그 숫자를 측정으로
바꾸는 것이 5절 스윕의 목적이다.

### 주사율 — 판정이 아니라 참고로 보고

폰의 네이티브 주사율 기준 p95(90Hz → 13.3ms, 120Hz → 10ms)를 **참고 줄**로만 띄운다.
팀 합격선은 "60fps"이고 `render/perf.js`의 드롭 판정도 16.7ms 기준이므로, 120Hz 폰이
16.7ms를 유지하면 문구상 합격이다. 다만 "120Hz 패널에서 60fps"는 수치가 시사하는 것보다
체감이 나쁘므로 기록은 남긴다. **합격선을 조일지는 Angerl의 결정이지 QA가 혼자 내릴 판단이
아니다** — 그래서 종료 코드/통과 여부에 반영하지 않는다.

### 하네스 자가검증 11개 중 10개 통과

에뮬레이트된 폰(412x915 @ DPR 2.625, CPU 4배 감속, ANGLE Metal)으로 wrapper 전체를
끝까지 구동해 저장된 JSON을 검사했다. 통과: 스위트 8행, 전 행 `sync` 채워짐, pixelRatio/
bufferPx 기록, 캡 스윕 4점, 기기 DPR 추가, 회귀 r²=0.993, 채움 판정 3줄 존재, 기종/주사율
기록, tainted=false. 유일한 실패는 wrapper의 `favicon.ico` 404가 폰 콘솔에 에러로 남는
것이었고 — 테스터에게 "에러를 보라"고 안내하는 화면에 생기는 잡음이라 — 204로 고쳤다.

### 이 과정에서 잡은 결함 3건 (전부 고침)

**거짓 통과 1건 — 헤드라인이 자격을 말하지 않았다 (영향: 상).** 자가검증이 `✅ 통과`를
띄웠다. 그 실행은 macOS + 1초 창이었다. 두 사실 모두 아래 advisory 줄에는 있었지만,
이슈에 붙는 것은 **헤드라인 스크린샷**이고 아무도 믿기 전에 스크롤하지 않는다.
`verdict.official`/`disqualifiers`를 추가했다 — `pass`는 "수치가 예산에 맞는다",
`official`은 "이 실행이 합격선이 요구하는 실행이다". 자격 미달이면 헤드라인이
`⚠️ 예산 내 — 공식 판정 아님`으로 바뀐다. 측정 창 단축과 비안드로이드 기기가
자격 박탈 사유다. 자가검증은 이제 데스크톱 실행이 평범한 통과로 표시되지 **않는지**를
검사한다.

**favicon 404 (영향: 하).** icon을 선언하지 않으면 브라우저가 *오리진 루트*의
`/favicon.ico`를 요청한다. 정적 호스트에서 이건 산출물 안의 무엇으로도 가로챌 수 없는
404다 — "에러를 보라"고 안내하는 화면에 에러가 생긴다. 빈 `data:` URL로 요청 자체를
없앴다. (LAN 경로는 204로 처리했지만 배포 경로에는 서버가 없다.)

**자가검증 자신의 오탐 2건.** 오프오리진 검사가 페이지 디렉터리와 비교해서 서브패스
배포의 자기 파일(`../bench/`, `/assets/`)을 서드파티로 신고했다 — 오리진 기준으로 고침.
발열 회귀 줄을 무조건 요구해서 단일 패스 실행에서 실패했다 — 패스 2개 이상일 때만
요구하게 고침.

## 9. 채움 속도 측정의 반복성 — 캡 2 결론의 오차 막대

스윕의 회귀 기울기가 DPR 캡 2를 받치는 유일한 수치이므로, 그 수치가 얼마나 흔들리는지
자체를 측정했다. 같은 머신에서 **출고 기본 샘플링**(`sweepsync=32`)으로 5회:

| 실행 | ms/Mpx | r² |
|---|---|---|
| 1 | 0.71 | 0.979 |
| 2 | 0.89 | 0.994 |
| 3 | 0.63 | 0.945 |
| 4 | 0.71 | 0.997 |
| 5 | 0.71 | 0.997 |

평균 **0.73 ms/Mpx**, 범위 0.63–0.89 (**±18%**). 5절에서 독립적으로 얻은 0.742와
일치한다. 샘플을 16개로 줄이면 0.49–1.06까지 벌어지고 r²이 0.444까지 떨어진다 —
**기본값 32는 적절하고, 줄이면 안 된다.**

왜 ±18%로 충분한가: 캡 2의 1.41Mpx 투사 비용이 **2.4–2.8ms**이고 예산은 16.7ms다.
여유가 약 **6배**이므로 측정 산포(±18%, 심지어 2배)가 결론을 뒤집지 못한다.
남은 불확실성은 측정 정밀도가 아니라 **"폰 GPU가 이 M1 Pro의 몇 분의 1인가"** 하나이고,
그것이 폰 왕복 1회가 측정할 값이다.
