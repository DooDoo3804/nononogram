## 4. 데스크톱 — 사람이 실제로 조준할 수 있는가

이슈가 요구한 "솔버가 유일해라고 한 것 vs 사람이 실제로 풀 수 있는 것"의 간극.

### 구조적 위험

`render/voxels.js`의 `pick()`은 **모든 셀**을 덮는 invisible `hit` InstancedMesh에
레이캐스트하고 `intersectObject(...)[0]` — **가장 앞의 셀**을 집는다. 셀을 MARKED로
칠해도 히트박스는 남는다. 그래서 클릭이 닿는 셀은 항상 그 레이 방향 최전면 셀이다.

24개 중 **21개**가 박스 내부(쉘이 아닌) 채움 셀을 갖는다 — `l4-cat` 112개 중 56개,
`l4-turtle` 58개 중 32개, `l3-rocket` 37개 중 23개. 내부 셀을 못 채우면 그 퍼즐은
끝까지 풀리지 않는다.

### 측정 방법

투사 수식을 다시 구현하지 않았다. 모든 샘플이 실제
`pointerup → view.rayFrom → grid.pick → session.cycle` 경로를 지나고, 결과는 세션이
내보내는 `cell` 이벤트로 읽는다. 렌더러와 어긋날 두 번째 수식 사본이 없다.

- **합성 PointerEvent** — 픽셀→셀 지도를 만드는 수천 번의 샘플. 실제 리스너·레이캐스트·
  세션을 지나지만 브라우저 자체 히트테스트는 지나지 않는다.
- **실제 CDP 입력** (`Input.dispatchMouseEvent` / `dispatchTouchEvent`) — 플레이와
  확인용. 브라우저 히트테스트를 지나므로 오버레이가 탭을 가로채면 여기서 드러난다.

셀이 "도달 가능"으로 보고되는 것은 **실제 이벤트가 그 셀에 닿은 경우뿐**이다.

### 결과

데스크톱 1280×860, 35개 카메라 각도 스윕 (`--step=10`). `px²`는 그 셀을 집을 수 있는
화면 면적 — 마우스 목표 하한 24×24 = 576px², 손가락 44×44 = 1936px².

읽는 법:

- **보드가 열린 각도에서 닿는 셀은 6³에서 216개 중 91개뿐이다.** 나머지는 카메라를
  돌려야 한다.
- **조준 면적이 급격히 작아진다.** 6³의 중앙값은 2300px²(≈48×48px)이지만, **49개 셀은
  24×24px보다 작고 98개는 44×44px보다 작다.** 최소는 100px² — 10×10px다.
- 퍼즐이 **실제로 요구하는** 셀만 보면: `l4-cat`은 필요한 112개 중 **40개가 24px 미만,
  66개가 44px 미만**. `l3-rocket`은 필요한 37개 중 **30개가 24px 미만**이다.

### 35각도 스윕이 닿지 못한 셀 — 퍼즐이 실제로 요구하는가

| 퍼즐 | 요구하지만 미도달 |
|---|---|
| `l4-castle` | 1개 — cell 37 = (1,0,1) |
| `l4-turtle` | 1개 — cell 74 = (2,2,2) |
| `l4-cat` | **10개** — (1,0,1) (2,0,2) (2,1,3) (3,0,2) (3,0,3) (3,1,2) (3,1,3) (3,2,3) (3,2,4) (4,0,2) |

나머지 21개 퍼즐은 요구 셀이 전부 도달 가능하다.

**이 셀들이 불가능한 것은 아니다.** 플레이어가 가진 카메라 조작을 전부 동원한 표적 탐색
(`probe` 모드 — 휠 줌으로 카메라를 **박스 안으로** 넣고 우클릭 드래그로 **팬**)을 돌려
3개를 되찾았고, 전부 **실제 클릭으로 확인**했다:

```
l4-cat cell 123: zoom 18t + az 45°  + pan [0, 0.25]   — real click CONFIRMED
l4-cat cell 116: zoom 22t + az 45°  + pan [0, 0.25]   — real click CONFIRMED
l4-cat cell  81: zoom 26t + az 225° + pan [0, -0.25]  — real click CONFIRMED
```

탐색은 3/10에서 중단했다 (설정당 ~6초, 280개 설정). 나머지 7개를 끝까지 돌리지 않았으므로
**"전부 도달 가능"이라고 주장하지 않는다.** 다만 성격은 분명하다 — **닿기는 하지만,
카메라를 퍼즐 내부로 밀어넣고 팬까지 해야 한다.** 게임은 이 조작을 가르치지도, 암시하지도
않는다. → DOO-17

## 9. 성능 항목 개정 — **합격** (재측정 없음)

보드가 `perf_gate = amend` 로 합격선을 교체했다. **DOO-12(실기 안드로이드 60fps 실측)는

| | |

## 10. 릴리스 노트에 반드시 들어갈 단서 2개 (보드 지시)

### 단서 1 — **실기 미검증**

이 판정은 **실제 폰에서 측정된 것이 아니다.** 재현되지 않은 축:

- 실제 폰 **GPU 메모리 대역폭** (ROP 처리량은 문헌 배율로 투사했을 뿐이다)
- **발열 스로틀링** — 수 분 플레이 후의 클럭 하강
- 기기 **브라우저 합성기**(Chrome on Android의 surface 합성 경로)

그리고 이 측정 방식 자체의 한계가 하나 있다 — **p95는 캡 안전성에 답하지 못한다.**
에뮬레이트된 폰에서 DPR 캡을 1 → 2.625로 쓸며 버퍼를 6.9배 키웠을 때:

| 캡 | 버퍼 픽셀 | p95 | sync | dropped |
|---|---|---|---|---|
| 1 | 351,848 | 17.60 | 1.70 | 0 |
| 1.5 | 791,658 | 17.30 | 1.90 | 0 |
| 2 | 1,407,392 | 17.70 | 2.40 | 0 |
| 2.625 | 2,422,521 | 17.50 | 3.20 | 0 |

**p95는 17.3–17.7ms로 완전히 평평하다.** GPU가 비동기로 래스터하므로 vsync를 놓치기
직전까지 60fps가 찍힌다. 움직이는 것은 `sync`(1.70 → 3.20ms)뿐이다. 따라서 위 §9의 p95
합격은 "프레임을 놓치지 않았다"는 뜻이고, "여유가 얼마나 남았는지"는 말하지 않는다.

### 단서 2 — **DPR 캡 2의 근거는 투사값이다**

`af5ea54`가 모바일 버퍼를 1배 → `min(DPR, 2)`로 올렸다. 캡 2를 고른 근거는 실측이 아니라
**실측 ÷ 문헌 배율**이다:

- 실측: M1 Pro / ANGLE Metal에서 채움 **0.95ms per Mpx** (412×915), r² > 0.99, 캡 1/1.5/2/2.625/3 × 3회
- 투사: 중간 크기 안드로이드의 ROP 처리량을 M1 Pro의 **1/5 ~ 1/10**로 가정 (문헌값, 핸드셋 판독 아님)
- 결과: 캡 2 → 1.41Mpx → 1.34ms → 10배에서 ~13.4ms. 캡 2.625 → ~23ms (예산 초과)
- 하한 괄호: 강제 SwiftShader에서 ~61ms/Mpx = M1 Pro의 **65~95배**. 거기서는 캡 1도 통과하지
  못한다(6³ p95 33ms). 폰 판정은 아니지만, 5~10배가 괄호의 가장자리가 아니라 **안쪽**에
  있음을 보인다 (DOO-20).

**주석 정리 — DOO-26, 해소됨 (`b317c88`).** 취소된 DOO-12를 "앞으로 답이 나올 곳"으로
가리키던 프로덕션 주석 2곳(`render/scene.js:141`, `scripts/bench-render.mjs:31`)은 플랫폼
트랙 파일이라 QA가 고치지 않고 **DOO-26으로 위임**했고, Vitra가 같은 하트비트 안에 고쳤다.
확인한 현재 문구:

```
render/scene.js:142   The physical device reading is no longer a release condition

                      bandwidth, thermal throttling and the browser compositor

render/scene.js:130   0.95ms/Mpx is the only measured term; the 5-10x it is divided

얘기다 — "글자가 양피지 위에서 ~2:1로 떨어지고 옆의 선은 ~5:1이었다".

4.5:1은 두 삼색을 가르는 선이다 (LIGHT 3.03~3.87 / DARK 4.73~5.11). 하한을 올리니
**사본이 전부 일치하면서 값만 낡은 트리는 이제 빨개진다.** 이건 DOO-9가 이미 내린 결정을
고정한 것이고 새 결정이 아니다 — 팔레트를 다시 튜닝하면 이 숫자도 같이 움직이되,
**diff에 드러나면서** 움직인다. 현재 브랜치(DARK)에서 `542/542` 초록, `eslint` 0.

#### 단, 가드는 10개 브랜치 중 **2개에만 있다**

| `tests/axis-colors.test.js` 보유 | 브랜치 |
|---|---|
| 있음 | `t-ui-peel`, `t-ui-viewport` |
| **없음** | `master`, `t-foundation`, `t-render`, `t-render-aim`, `t-rewards`, `t-solver`, `t-ui`, `t-ui-stroke-undo` |

그래서 §12.2의 "적신호 5개"는 **가드가 거기 있었다면 냈을 판정**이고, 실제로는 그 5개
브랜치에서 가드가 돌지 않는다. **`master`에도 아직 없다.** 가드는 그것을 담은 브랜치가
머지된 뒤에야 릴리스를 지킨다 → §12.6의 통합 순서 조건.

### 12.4 통합 병합은 `style.css`에서 실제로 충돌한다

브랜치를 `master`에 차례로 쌓아(각 단계를 `git commit-tree`로 커밋화해 다음 병합의 한 쪽으로
넘긴다) 돌린 결과:

| 누적 단계 | 결과 | 비고 |
|---|---|---|
| `+t-foundation` | 초록 LIGHT/LIGHT | — |
| `+t-render` → `+t-solver` | **적신호** LIGHT/DARK | gizmo만 보정값, CSS는 낡음 |
| `+t-ui` | **적신호** — `style.css` **충돌**, 낡은 `rgba()` **6곳** | 충돌 마커 발생 |
| `+t-ui-peel` → `+t-ui-viewport` | **적신호** — `--axis-x/y/z`가 **각각 두 번 선언** | 마커 잔존 |

즉 `t-ui` 단계부터 **`style.css`가 실제로 충돌하고**, 최종 트리는 `--axis-*`를 **중복
선언한다**. 이건 가드의 "각 축 변수를 정확히 한 번 선언한다" 어서션이 존재하는 이유 그대로다.

이것을 "릴리스가 깨졌다"로 읽지는 않는다 — 사람이 충돌을 해소하지 않은 **기계적 병합**의
결과다. 정확한 진술은 이렇다: **실릴 축 삼색은 통합 담당자의 충돌 해소 시점에 결정되고,
틀린 해소를 잡아주는 것은 이 가드뿐이며, 가드는 §12.3의 "일치하지만 낡은" 해소를 잡지
못한다.** 통합 시 `--axis-*`가 `#9e3f2c / #436a39 / #3d5c8c`인지 눈으로 확인할 것.

### 12.5 DOO-23의 남은 범위

Pixa가 고친 것은 `t-ui-viewport` 한 브랜치다. DOO-23의 제목이 가리키는 **적신호 5개
(`t-render`, `t-render-aim`, `t-rewards`, `t-ui`, `t-ui-stroke-undo`)는 전부 그대로 남아
있다** — 고쳐진 브랜치는 그 5개에 애초에 포함되지 않았다. 어느 쪽 값이 정답인지는 여전히
디자인 결정이므로 QA가 정하지 않는다 → DOO-23 (Pixa)에 위 표를 그대로 전달했다.

**DOO-23은 `done`으로 닫혔다** (Pixa, `e7d98f3`). QA는 그 종료에 이의를 달지 않는다 —
남아 있던 위험의 본체(§12.3의 "일치하지만 낡은" 해소가 조용히 통과하는 경로)를 이
하트비트에 4.5:1 하한으로 막았기 때문이다. 다만 **DOO-23 제목이 센 "적신호 5개 브랜치"
자체는 수정되지 않았다**는 사실은 기록해 둔다. 그 5개는 머지 시점에 가드가 잡는다 —
**가드가 `master`에 들어와 있다면.** 그래서 남는 것은 수정 작업이 아니라 통합 순서 조건
하나다 (§12.6).

### 12.6 통합 체크리스트 — 이 두 줄이 릴리스 판정의 전제다

1. **`t-ui-viewport`(또는 `t-ui-peel`)를 먼저 머지해 `master`에 가드를 올린다.** 그 전에
   다른 브랜치를 머지하면 §12.2의 드리프트가 아무 저항 없이 통과한다.
2. 통합 후 `node tests/axis-drift-branches.mjs` 와 `npx vitest run tests/axis-colors.test.js`
   를 돌려, `--axis-*`가 `#9e3f2c / #436a39 / #3d5c8c`이고 `--axis-*` 중복 선언이 없음을
   확인한다 (§12.4의 기계적 병합은 중복 선언을 만든다).

QA는 값의 선택을 하지 않는다. 위 두 줄은 **이미 내려진 결정(DOO-9)이 실제로 실리는지**를
확인하는 절차다.

### 판정 시작 전 다시 돌릴 것

선행이 전부 닫혔다는 신호를 받으면, 깨끗한 트리에서 이 순서로 돌린 뒤 §1의 판정 표를
다시 채운다. 재측정 대상은 **성능이 아니라 플레이 가능성과 게이트**다 (§9는 확정).

node tests/playtest.mjs play  http://127.0.0.1:4173 qa-out --platform=mobile
node tests/playtest.mjs play  http://127.0.0.1:4173 qa-out --platform=desktop
node tests/playtest.mjs edge  http://127.0.0.1:4173 qa-out --platform=mobile
```
